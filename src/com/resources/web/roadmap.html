Where the Server Is Headed

The plan · September 2026

This project is a learning journey: build a real HTTP server by hand, then layer on features one at a time. Here is the roadmap we are following.

Done So Far

Phase B is complete: the method enum covers GET/HEAD/POST/PUT/DELETE, non-GET methods read a request body bounded by Content-Length (oversized bodies get 413), and the server returns the status codes it needs — 200, 201, 400, 404, 413, 414, 500, 501, 505. Phase C is also done: a path-aware Router dispatches /api/* requests by method and path, extracts {id} path variables, parses JSON bodies, and hands off to a TodoStore (backed by a ConcurrentHashMap with AtomicLong ids). All five todo endpoints are wired and unit-tested. And Phase D is done: RequestHandler now runs each HTTPWorker on a hand-written bounded thread pool (MyExecutorService) instead of spawning a thread per connection, and parallel POSTs are proven to produce unique ids.

Next Up

Phase E: a single-page browser frontend using fetch() against the todo API. We would also like to use conventional reason phrases (OK instead of Success), consistent header spacing, and request logging via the SLF4J setup already in lib/.

Eventually

Persistent storage for the todo store so data survives a restart, plus repeated-request handling via keep-alive connections instead of closing the socket after every response.

"Building it by hand first makes every framework you meet later feel like magic you can peek under."
