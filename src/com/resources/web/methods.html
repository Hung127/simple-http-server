HTTP Methods We Support

What the parser understands · September 2026

Every request line begins with a method — a verb that tells the server what the client wants to do. Our server implements GET, HEAD, POST, PUT, and DELETE, and rejects anything else as unimplemented.

GET

The workhorse of the web. GET asks the server to retrieve a resource. In our implementation it reads the requested file from the web root and returns it with the proper Content-Type header — or, under an /api/ path, invokes the matching API handler. Because GET is a safe, read-only operation, browsers and caches rely on it heavily for loading pages, stylesheets, and images.

HEAD

Identical to GET, except the server omits the response body. It is handy for checking whether a resource exists or reading its headers without downloading content. Our HTTPParser recognizes HEAD just like GET.

POST

Used to create a resource. POST asks the server to process a request body — in this project, POST /api/todos parses the incoming JSON and creates a new todo, answering with 201 Created. Working with bodies means the parser must honor Content-Length and guard against oversized payloads.

PUT

Used to update a resource. PUT /api/todos/{id} accepts a JSON body containing title, completed, or both, and applies a partial update to the matching todo.

DELETE

Used to remove a resource. DELETE /api/todos/{id} removes the todo and answers with an empty 200 Success. Because our parser reads bodies for every non-GET method, clients send Content-Length: 0 even when there is nothing to upload.

"The parser decides what the client asked for; the router decides how to answer."

Unknown Methods

Tokens outside this set — including PATCH and OPTIONS, which some clients expect but we have not implemented yet — or tokens longer than the longest known method are rejected with 501 Not Implemented, keeping the surface area explicit.

Served by a hand-written Java HTTP server. See them in action on the API page.
